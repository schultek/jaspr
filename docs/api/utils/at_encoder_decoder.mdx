With the `@encoder` and `@decoder` annotations you can set up custom serialization for any type. This is used
by Jaspr for both:

- (de-)serializing parameters of [@client](/api/utils/at_client) components
- (de-)serializing fields using the [@sync](/api/utils/at_sync) annotation

## Usage

To enable custom serialization for your data class use the annotations in the following way:

- The `@decoder` annotation must be used on a **constructor** or **static method** that returns an instance of the class
  and has either:
  - Exactly one parameter of any primitive serializable type (`bool`, `int`, `String`, `Map<String, dynamic>`, etc.).
  - Two parameters, where the second parameter is a `ComponentMount` function (`Component Function(String)`) to decode [Server Components](/going_further/server_components) in `@client` components (see below).

- The `@encoder` annotation must be used on an **instance method** that returns the same raw type that the
  `@decoder` method takes in as its first parameter.

- Both methods can have any name.

In practice this can look like this:

```dart title="model.dart"
class Model {
  // Constructors, fields, etc.
  /* ... */

  @decoder
  static Model decode(Map<String, dynamic> data) => /* ... */;

  @encoder
  Map<String, dynamic> encode() => /* ... */;
}
```

<Info>
The annotations are designed to be compatible with virtually any serialization package like `json_serializable`
or `dart_mappable`. Simply annotate the methods generated by these packages either directly, or by using a wrapper method.
</Info>

While `Map<String, dynamic>` is the most common type for serializing Dart classes, you can also use other primitive types
like `String`, `List<dynamic>` etc. as long as the encoding method returns the same type as the decoding method accepts.

An enum can use the annotations the same way, for example to serialize its values by name:

```dart title="color.dart"
enum Color {
  red,
  green;

  @decoder
  static Color fromName(String name) => Color.values.byName(name);

  @encoder
  String toName() => name;
}
```

## Customize serialization of third-party types

Sometimes, you cannot control the methods of a class, such as when using a third-party library.
In these cases, you can create a custom override type which "redefines" the type for serialization.

For example, consider the case where the `Model` class is imported from a third-party library, `package:model`.
Since we do not own `package:model`, we cannot change the methods of the `Model` class.

Instead of modifying the `Model` class, we can define a custom override for `Model` which will be used in place of the
original `Model` class when it's used for serialization in Jaspr.

```dart title="lib/model_override.dart"
import 'package:jaspr/jaspr.dart';
import 'package:model/model.dart';

// We create an extension type which wraps over the third-party type and
// defines the @decoder and @encoder methods
//
// Since the extension type implements the original type, it will behave
// identically to the original except for the serialization logic.
extension type ModelOverride(Model model) implements Model {
  @decoder
  factory ModelOverride.decode(Map<String, dynamic> data) {
    return ModelOverride(
      Model(
        // decode the values of [data]
        /* ... */
      ),
    );
  }

  @encoder
  Map<String, dynamic> encode() => {
      // encode the values of [model]
      /* ... */
    };
}
```

Custom overrides are defined as [extension types](https://dart.dev/language/extension-types) which wrap and implement
the original type. You must always implement the original type in your extension type.

## Decoding models with Component fields (Server Components)

When passing custom data classes into `@client` components, your models can also have `Component` fields (such as tabs, cards, or custom layouts).

On the server, when a `@client` component is rendered during SSR, Jaspr automatically encodes any nested `Component` inside your `@encoder` output into a Server Component marker ID (e.g. `"s@1"`).

To decode these components on the client, your `@decoder` function can accept a `ComponentMount` parameter:

```dart title="tab_item.dart"
import 'package:jaspr/jaspr.dart';

class TabItem {
  final String label;
  final Component content;

  const TabItem({required this.label, required this.content});

  @decoder
  factory TabItem.fromJson(Map<String, dynamic> json, ComponentMount mount) {
    return TabItem(
      label: json['label'] as String,
      content: mount(json['content'] as String),
    );
  }

  @encoder
  Map<String, dynamic> toJson() => {
    'label': label,
    'content': content,
  };
}
```

During client-side hydration, Jaspr automatically detects that your `@decoder` function expects `ComponentMount` and provides the mount function to resolve the server component markers back into `Component`s.

### Parameter format: Positional or Named

The mount parameter can be either positional or named:

```dart
// Positional (required or optional):
@decoder
static CardData decode(Map<String, dynamic> data, ComponentMount mount) => ...

// Named (required or optional):
@decoder
static CardData decode(Map<String, dynamic> data, {ComponentMount? mount}) => ...
```

### Optional / Nullable Components

For nullable `Component?` fields:

```dart
header: json['header'] != null ? mount(json['header'] as String) : null,
// or using a switch expression:
header: switch (json['header']) { String id => mount(id), _ => null },
```

### Collections of Components

For lists or maps of components inside custom models:

```dart
items: (json['items'] as List).cast<String>().map(mount).toList(),
```

<Info>
`ComponentMount` is only supported across `@client` component boundaries. It cannot be used with `@sync` fields, as state synchronization does not support Server Components.
</Info>
